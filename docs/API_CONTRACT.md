
# ExpiryWatch — API Contract

## Дополнения интеграционной ветки

Локальный интерфейс доступен на `/ui/`; корневой `/` сохраняет прежний JSON-ответ.
Пути API, поля, статусы, PUT/PATCH и ответ DELETE (`200`, `{"id": ...}`) сохранены.

- Общие правила применяются к POST, PUT и PATCH. PATCH проверяет итоговую запись после объединения с сохранёнными данными.
- Название — от 1 до 255 символов после удаления пробелов по краям; единица измерения — от 1 до 16 символов.
- Количество — конечное JSON-число больше нуля, не больше `99999999.99`, с точностью до двух знаков после запятой (`NUMERIC(10,2)`). Строки и boolean запрещены.
- ID справочников — положительные целые JSON-числа, соответствующие существующим записям.
- Даты — календарные строки `YYYY-MM-DD` или `null`. Если обе даты указаны, `expiry_date >= purchase_date`. Равные даты и просроченные продукты допустимы.
- Неизвестные поля запрещены. `storage_id` и `expiration_date` не являются альтернативными именами полей.
- Ошибки валидации сохраняют строковый `detail` и дополнительно возвращают `errors: [{"loc": ["body", "quantity"], "msg": "Значение должно быть больше нуля"}]` для полей формы. Сообщения переведены на русский.
- При конфликте ограничений БД возвращается 409 с понятным `detail`, без SQL и внутренних данных.
- GET `/stats/` возвращает статистику всех позиций независимо от фильтров списка.

В SQLite операции записи блокируются до чтения записи: конкурирующие PATCH не обходят проверку порядка дат.
Схема существующей БД автоматически не изменяется; интеграция не запускает скрипты миграции и не удаляет данные.

## 1. Общая информация

Документ описывает API-контракт Backend 1 проекта ExpiryWatch для взаимодействия с frontend.

Backend разработан на FastAPI и использует SQLAlchemy и SQLite для работы с базой данных.

**Репозиторий:** https://github.com/ExpiryWatch/backend1

**Ветка:** `feature/backend-setup`

**Локальный адрес API:** `http://127.0.0.1:8000`

**Swagger UI:** `http://127.0.0.1:8000/docs`

**Формат данных:** JSON (`application/json`).

Указанный адрес используется при локальном запуске backend. При интеграции frontend и backend адрес сервера может отличаться.

## 3. Общие правила взаимодействия

- Все запросы с телом используют JSON.
- ID продукта передаётся в адресе запроса как `item_id`.
- ID категорий и мест хранения передаются целыми числами.
- Даты передаются в формате `YYYY-MM-DD`.
- При успешном выполнении API возвращает HTTP 200 или 201.
- При отсутствии продукта возвращается HTTP 404.
- При некорректных входных данных возвращается HTTP 422.
- Формат обрабатываемых ошибок: `{"detail": "Текст ошибки"}`.
- Поля `status`, `status_label` и `days_left` рассчитываются backend автоматически.


## 4. Поля продукта

### 4.1. Структура ответа InventoryRead

При получении, создании или обновлении продукта API возвращает объект со следующими полями:

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | Уникальный ID продукта |
| `name` | string | Название продукта |
| `quantity` | number | Количество продукта |
| `unit` | string | Единица измерения |
| `category_id` | integer / null | ID категории |
| `storage_location_id` | integer / null | ID места хранения |
| `purchase_date` | string / null | Дата покупки |
| `expiry_date` | string / null | Конечный срок годности |
| `comment` | string / null | Комментарий |
| `status` | string | Статус срока годности |
| `status_label` | string | Название статуса на русском языке |
| `days_left` | integer / null | Количество дней до окончания срока годности |
| `created_at` | string | Дата и время создания записи |
| `updated_at` | string | Дата и время последнего обновления |

Даты передаются в формате `YYYY-MM-DD`.

Поля `created_at` и `updated_at` возвращаются в формате ISO 8601.


### Правила валидации поля `unit`

- Тип: `string`.
- Значение не может быть `null`.
- Пустая строка `""` и строка из одних пробелов запрещены.
- Пробелы в начале и конце строки автоматически удаляются.
- POST: поле необязательное, по умолчанию `"шт"`.
- PUT: поле обязательное.
- PATCH: поле необязательное; если не передано, значение не изменяется.
- При нарушении правил возвращается HTTP 422.

Пример ошибки:

```json
{
  "detail": "body.unit: Value error, Единица измерения не может быть пустой"
}
```


### 4.2. Поля для создания и обновления

| Поле | POST | PUT | PATCH |
|---|---|---|---|
| `name` | Обязательно | Обязательно | Необязательно |
| `quantity` | Обязательно | Обязательно | Необязательно |
| `unit` | Необязательно | Обязательно | Необязательно |
| `category_id` | Необязательно | Обязательно | Необязательно |
| `storage_location_id` | Необязательно | Обязательно | Необязательно |
| `purchase_date` | Необязательно | Обязательно | Необязательно |
| `expiry_date` | Необязательно | Обязательно | Необязательно |
| `comment` | Необязательно | Обязательно | Необязательно |

**Правила:**

- `name` — непустая строка, название из одних пробелов запрещено.
- `quantity` — число строго больше 0. Дробные значения разрешены.
- `unit` — единица измерения, при создании по умолчанию `"шт"`.
- `category_id` — ID существующей категории или `null`.
- `storage_location_id` — ID существующего места хранения или `null`.
- `purchase_date` — дата покупки или `null`.
- `expiry_date` — конечный срок годности или `null`.
- `comment` — текст комментария или `null`.

Конечная дата годности может находиться в прошлом. В таком случае продукт сохраняется со статусом `expired`.

### 4.3. Поля только для чтения

Следующие поля рассчитываются или устанавливаются backend:

- `id`
- `status`
- `status_label`
- `days_left`
- `created_at`
- `updated_at`

Frontend не должен передавать эти поля в теле POST, PUT или PATCH.

### 4.4. Особенности PUT и PATCH

**PUT** требует передачи всех восьми изменяемых полей продукта.

Если какое-либо поле отсутствует, сервер возвращает HTTP 422.

**PATCH** изменяет только явно переданные поля. Остальные значения сохраняются без изменений.

При PATCH запрещено передавать `null` для:

- `name`
- `quantity`
- `unit`

Для необязательных полей, например `comment` и `expiry_date`, значение `null` разрешено.

Если поле отсутствует в PATCH-запросе, его текущее значение сохраняется.


## 5. Статусы срока годности

Backend автоматически рассчитывает статус продукта по полю `expiry_date`.

| Статус | Условие |
|---|---|
| `fresh` | До окончания срока годности больше 3 дней |
| `expiring_soon` | До окончания срока осталось от 0 до 3 дней включительно |
| `expired` | Дата окончания срока уже прошла |
| `no_date` | Срок годности не указан |

### Дополнительные поля

- `status` — техническое значение статуса.
- `status_label` — человекочитаемое название статуса на русском языке.
- `days_left` — количество дней до окончания срока годности.

Примеры значений `days_left`:

| Значение | Значение для пользователя |
|---|---|
| `5` | Осталось 5 дней |
| `1` | Остался 1 день |
| `0` | Последний день срока годности |
| `-2` | Срок закончился 2 дня назад |
| `null` | Срок не указан |

Frontend должен использовать поле `status` для выбора оформления продукта, а `status_label` — для отображения названия статуса пользователю.

Статус рассчитывается на основе текущей даты, поэтому может изменяться без редактирования продукта.

## 6. Примеры запросов

### 6.1. Создание продукта — POST

Endpoint:

`POST /inventory/`

Request body:

```json
{
  "name": "Молоко",
  "quantity": 2,
  "unit": "л",
  "category_id": 1,
  "storage_location_id": 1,
  "purchase_date": "2026-11-19",
  "expiry_date": "2026-11-25",
  "comment": null
}
```

Успешный HTTP-код: `201 Created`.

Ответ содержит полный объект продукта со всеми полями из `InventoryRead`.

### 6.2. Полное обновление — PUT

Endpoint:

`PUT /inventory/1`

Request body:

```json
{
  "name": "Молоко",
  "quantity": 3,
  "unit": "л",
  "category_id": 1,
  "storage_location_id": 1,
  "purchase_date": "2026-11-19",
  "expiry_date": "2026-11-25",
  "comment": null
}
```

Успешный HTTP-код: `200 OK`.

Все восемь изменяемых полей должны присутствовать в запросе.

### 6.3. Частичное обновление — PATCH

Endpoint:

`PATCH /inventory/1`

Request body:

```json
{
  "quantity": 5
}
```

Успешный HTTP-код: `200 OK`.

Изменяется только `quantity`. Остальные поля сохраняют свои прежние значения.

### 6.4. Удаление продукта — DELETE

Endpoint:

`DELETE /inventory/1`

Успешный HTTP-код: `200 OK`.

Response body:

```json
{
  "id": 1
}
```

### 6.5. Получение продукта без срока годности — GET

Endpoint:

`GET /inventory/6`

Пример ответа:

```json
{
  "id": 6,
  "name": "Соль",
  "quantity": 1,
  "unit": "кг",
  "category_id": 5,
  "storage_location_id": 3,
  "purchase_date": null,
  "expiry_date": null,
  "comment": null,
  "status": "no_date",
  "status_label": "Срок не указан",
  "days_left": null,
  "created_at": "2026-11-15T18:54:12.606617",

```

Это пример из тестовой базы. ID продуктов в базах других разработчиков могут отличаться.


## 7. Поиск, фильтрация и сортировка

Метод `GET /inventory/` поддерживает параметры запроса для поиска, фильтрации, сортировки и пагинации продуктов.

### 7.1. Параметры запроса

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `q` | string | null | Поиск по названию |
| `category_id` | integer | null | Фильтр по категории |
| `storage_location_id` | integer | null | Фильтр по месту хранения |
| `status` | string | null | Фильтр по статусу годности |
| `sort` | string | `name` | Поле сортировки |
| `order` | string | `asc` | Направление сортировки |
| `limit` | integer | null | Максимальное количество записей |
| `offset` | integer | 0 | Количество пропускаемых записей |

Допустимые значения:

- `status`: `fresh`, `expiring_soon`, `expired`, `no_date`.
- `sort`: `name`, `expiry`.
- `order`: `asc`, `desc`.
- `limit`: целое число от 1.
- `offset`: целое число от 0.

Если фильтры не указаны, возвращаются все продукты.

### 7.2. Примеры запросов

Поиск по названию:

```http
GET /inventory/?q=молоко
```

Фильтрация по категории:

```http
GET /inventory/?category_id=1
```

Получение просроченных продуктов:

```http
GET /inventory/?status=expired
```

Сортировка по ближайшему сроку годности:

```http
GET /inventory/?sort=expiry&order=asc
```

Пагинация:

```http
GET /inventory/?limit=3&offset=3
```

Комбинированный запрос:

```http
GET /inventory/?category_id=1&status=expired&sort=expiry&order=asc
```

### 7.3. Формат ответа

При успешном запросе возвращается HTTP `200 OK`.

Ответ представляет собой JSON-массив объектов `InventoryRead`:

```json
[
  {
    "id": 1,
    "name": "Молоко",
    "quantity": 2,
    "unit": "л",
    "category_id": 1,
    "storage_location_id": 1,
    "purchase_date": "2026-11-13",
    "expiry_date": "2026-11-25",
    "comment": null,
    "status": "fresh",
    "status_label": "Годен",
    "days_left": 5,
    "created_at": "2026-11-15T18:54:12.606610",
    "updated_at": "2026-11-20T17:15:36.828727"
  }
]
```

Пример приведён для иллюстрации структуры. Статусы и количество оставшихся дней рассчитываются на момент запроса.

Если подходящих продуктов нет, возвращается пустой массив:

```json
[]
```

Ответ не содержит отдельных полей `total`, `page` или `pagination`.

Параметр `offset` применяется при переданном `limit`.

| Поле | Тип | Описание |

| `id` | integer | ID категории |
| `name` | string | Название категории |
| `items_count` | integer | Количество продуктов |

### 8.2. Получение мест хранения

Endpoint:

`GET /storage-locations/`

Успешный HTTP-код: `200 OK`.

Пример ответа:

```json
[
  {
    "id": 1,
    "name": "Холодильник",
    "icon": "snowflake",
    "items_count": 3
  },
  {
    "id": 3,
    "name": "Кухонный шкаф",

  }

```

Поля места хранения:

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | ID места хранения |

| `icon` | string / null | Значок места хранения |

### 8.3. Правила работы со справочниками

- Категории и места хранения возвращаются в виде JSON-массивов.
- Пустые категории и места хранения также присутствуют в ответе.
- Для пустых категорий и мест хранения `items_count` равен 0.
- Frontend использует `id` категории и места хранения при создании и обновлении продуктов.
- Названия категорий и мест хранения необходимо получать из API, а не задавать вручную в frontend.


## 9. HTTP-коды и обработка ошибок

### 9.1. Коды ответов API

| Метод | Endpoint | Успешный код | Возможные ошибки |
|---|---|---|---|
| GET | `/inventory/` | 200 | 422 |
| GET | `/inventory/{item_id}` | 200 | 404, 422 |
| POST | `/inventory/` | 201 | 422 |
| PUT | `/inventory/{item_id}` | 200 | 404, 422 |
| PATCH | `/inventory/{item_id}` | 200 | 404, 422 |
| DELETE | `/inventory/{item_id}` | 200 | 404, 422 |
| GET | `/categories/` | 200 | — |
| GET | `/storage-locations/` | 200 | — |

Таблица описывает предусмотренные приложением успешные ответы и основные клиентские ошибки. Внутренние ошибки сервера также возможны.

### 9.2. Формат ошибок

Обрабатываемые ошибки API возвращаются в формате:

```json
{
  "detail": "Текст ошибки"
}
```

Поле `detail` содержит строку с описанием проблемы.

Frontend должен ориентироваться на HTTP-код ответа, а текст `detail` использовать для отображения сообщения пользователю.

### 9.3. Ошибка 404 — продукт не найден

Возникает, если пользователь запрашивает, обновляет или удаляет несуществующий продукт.

Пример ответа:

```json
{
  "detail": "Inventory item with ID 99999 not found"
}
```

### 9.4. Ошибка 422 — некорректные данные

Возникает при неправильных параметрах запроса или ошибках валидации.

Примеры:

Отрицательное количество:

```json
{
  "detail": "body.quantity: Input should be greater than 0"
}
```

Несуществующая категория:

```json
{
  "detail": "Категория с ID 999999 не найдена"
}
```

Несуществующее место хранения:

```json
{
  "detail": "Место хранения с ID 999999 не найдено"
}
```

Передача `null` в обязательное поле при PATCH:

```json
{
  "detail": "Поле quantity не может быть null"
}
```

Неполный PUT также возвращает 422 с перечислением отсутствующих полей.

### 9.5. Рекомендации по обработке ошибок

Frontend должен:

- Проверять HTTP-код каждого ответа.
- Обрабатывать 404, если продукт не найден.
- Обрабатывать 422 при некорректных данных.
- Показывать пользователю сообщение из `detail`.
- Не сравнивать сообщения об ошибках по точному тексту.
- Предусматривать обработку сетевых ошибок и ошибок сервера.

Не следует считать, что все возможные ошибки сервера всегда имеют поле `detail`: единый строковый формат предусмотрен для обрабатываемых клиентских ошибок API.

## 10. Рекомендации по интеграции frontend и backend

### 10.1. Работа с продуктами

- Для получения списка использовать GET `/inventory/`.
- Для создания использовать POST `/inventory/`.
- Для полной замены данных использовать PUT `/inventory/{item_id}`.
- Для изменения отдельных полей использовать PATCH `/inventory/{item_id}`.
- Для удаления использовать DELETE `/inventory/{item_id}`.

### 10.2. Работа со статусами

Frontend не должен самостоятельно изменять статус срока годности.

Для определения состояния продукта использовать поле `status`.

Для отображения названия статуса использовать `status_label`.

Для отображения количества оставшихся дней использовать `days_left`.

### 10.3. Работа с категориями и местами хранения

Категории получать через GET `/categories/`.

Места хранения получать через GET `/storage-locations/`.

При создании или обновлении продукта передавать соответствующие числовые ID.

Не следует рассчитывать на фиксированные ID демонстрационных категорий и мест хранения, поскольку они могут отличаться между базами данных.

### 10.4. Согласование интеграции

При локальном запуске backend использует адрес:

`http://127.0.0.1:8000`

Если frontend запускается на другом адресе или порту, необходимо согласовать настройки CORS и адрес API.

Изменения полей, типов данных, формата ошибок и поддерживаемых статусов должны согласовываться между frontend и backend.

### 10.5. Документация

## 11. Статистика продуктов

### GET `/stats/`

Возвращает общую статистику продуктов из базы данных.

Параметры запроса отсутствуют.

Успешный HTTP-код: `200 OK`.

Пример ответа:

```json
{
  "total": 7,
  "fresh": 2,
  "expiring_soon": 1,
  "expired": 3,
  "no_date": 1
}
```

### Поля ответа

| Поле | Тип | Описание |
|---|---|---|
| `total` | integer | Общее количество позиций |
| `fresh` | integer | Количество годных продуктов |
| `expiring_soon` | integer | Количество продуктов с истекающим сроком |
| `expired` | integer | Количество просроченных продуктов |
| `no_date` | integer | Количество продуктов без срока годности |

Все значения рассчитываются автоматически по текущим данным базы.

Статистика отражает количество позиций, а не сумму значений `quantity`.

При изменении данных статистика пересчитывается при следующем запросе.
